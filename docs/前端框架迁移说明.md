# 前端框架迁移说明

**迁移阶段：** Phase 1（基础设施落地）  
**技术栈：** Vue 3 + Vite + Vue Router + Pinia  
**完成日期：** 2026-11-10  
**影响范围：** 仅新增 `/app/` 入口与 `frontend/` 工程，未改动主播端、观众端的任何业务代码

---

## 1. 背景与目标

项目原始前端是两套单文件原生页面：

- 主播运营台：`src/live_commerce/index.html`，约 4,700 行，内联 CSS / JavaScript；
- 观众 H5：`src/viewer/index.html`，约 2,100 行，同样单文件内联。

这种形态部署简单、评审可直接查看源码，但缺少组件化、模块系统、路由与状态管理，不利于后续多人协作和功能扩展。传智杯评审对前端工程化有明确要求，因此启动框架迁移。

Phase 1 的目标不是一次性重写全部业务，而是**先把框架基础设施跑通，并保证现有功能零回归**：

1. 引入 Vue 3 工程化构建链（Vite）；
2. 用 Vue Router 管理页面路由，用 Pinia 管理登录态；
3. 完整迁移体量较小的登录页，验证框架能力；
4. 主播端与观众端通过**同源 iframe 桥**接入新框架，布局与交互 100% 保留；
5. 旧入口 `/live-commerce/`、`/login`、`/viewer` 全部保留，可随时回滚。

> 约束：本阶段**只改造基础架构与文档，不改动其它业务代码**。因此没有直接拆解 4,700 行的运营台，而是采用渐进式迁移（Strangler Fig Pattern），后续按页面逐块替换。

## 2. 迁移策略：外壳 + 旧页桥接

```
/app/#/login     → Vue 登录页（已完整迁移）
/app/#/host      → Vue 外壳 → <iframe src="/live-commerce/">  → 原生主播运营台
/app/#/viewer    → Vue 外壳 → <iframe src="/viewer">          → 原生观众 H5
```

### 2.1 为什么用 iframe 桥接

| 方案 | 优点 | 风险 |
| --- | --- | --- |
| 直接重写运营台 | 一步到位 | 4,700 行单文件，重写周期长，回归风险高，违背“不改业务代码”约束 |
| 复制一份新页面再改 | 可自由重构 | 两份业务代码并行，修 bug 要改两处，必然漂移 |
| **同源 iframe 桥接** | 旧页面零改动、布局交互 100% 保留、可随时回滚 | URL 停留在外壳路由；跨 iframe 通信需约束 |

选择 iframe 桥接，是因为它把“框架迁移”和“业务重写”解耦：Phase 1 只证明新框架能承载入口、路由、鉴权与构建部署；Phase 2 再逐页把 iframe 内的内容替换为 Vue 组件，替换一块、删除一块，风险可控。

### 2.2 同源带来的便利

新旧页面由同一个 FastAPI 服务、同一个端口提供，因此：

- `localStorage` 共享：Vue 登录页写入的 `lc_auth_token` / `lc_auth_user`，iframe 内的运营台可直接读取；
- Cookie 共享：后端 `/auth/login` 下发的 HttpOnly `lc_host_token` 自动随 iframe 请求发送；
- 不需要 `postMessage` 桥接身份，也不需要额外 CORS 配置；
- WebSocket 仍由 iframe 内的旧页面建立，外壳不重复建连。

### 2.3 代价与边界

- 浏览器地址栏显示 `/app/#/host`，而不是 iframe 内部的页面状态；刷新后仍回到运营台首页，iframe 内部页面不参与浏览器历史；
- 旧页面的 `alert` / 下载 / 新窗口行为受 iframe 沙箱能力影响，已在 `LegacyFrame.vue` 中通过 `allow="camera; microphone; autoplay; clipboard-write"` 放开必要权限；
- iframe 内页面的标题不会自动同步到浏览器标签页，当前由外壳统一设置。

这些代价在 Phase 2 逐页替换后会自然消失。

## 3. 技术选型

| 层次 | 选型 | 版本 | 说明 |
| --- | --- | --- | --- |
| 视图框架 | Vue | `^3.5.13` | Composition API + `<script setup>` |
| 构建工具 | Vite | `^6.0.7` | 开发态 HMR、生产态静态构建 |
| 路由 | Vue Router | `^4.5.0` | Hash 模式，避免服务端 SPA fallback |
| 状态管理 | Pinia | `^2.3.1` | 当前仅 `auth` 一个 store |
| 单文件组件 | `@vitejs/plugin-vue` | `^5.2.1` | `.vue` 编译 |

选择 Hash 路由（`createWebHashHistory`）而不是 History 路由，原因：

1. FastAPI 只用 `StaticFiles(html=True)` 托管构建产物，没有为 `/app/*` 写 SPA fallback；
2. Hash 路由的 `#` 之后不会发送到服务端，刷新 `/app/#/host` 永远命中 `index.html`；
3. 部署到任意静态服务器（nginx / OSS / CDN）都不需要额外的 rewrite 规则。

## 4. 目录结构

```
frontend/
├─ index.html                 # Vite 入口，挂载 #app
├─ package.json               # 依赖与 dev/build 脚本
├─ package-lock.json          # 锁定依赖版本
├─ vite.config.js             # base=/app/、outDir=app-dist、开发代理
├─ app-dist/                  # 生产构建产物（随源码提交）
│  ├─ index.html
│  └─ assets/
│     ├─ index-*.js
│     └─ index-*.css
└─ src/
   ├─ main.js                 # createApp + Pinia + Router
   ├─ App.vue                 # <router-view />
   ├─ router/index.js         # 路由表与登录守卫
   ├─ stores/auth.js          # 登录 / 注册 / 会话检查 / 退出
   ├─ styles/base.css         # 全局重置与全屏布局
   ├─ components/
   │  └─ LegacyFrame.vue      # 同源 iframe 桥，带加载态
   └─ views/
      ├─ LoginView.vue        # 完整迁移的登录 / 注册页
      ├─ HostView.vue         # 主播端外壳
      └─ ViewerView.vue       # 观众端外壳
```

### 4.1 为什么构建目录叫 `app-dist` 而不是 `dist`

仓库根 `.gitignore` 全局忽略了 `dist/`（Python 打包产物习惯）。如果 Vite 使用默认 `dist`，构建产物不会进入版本库，评委拉取代码后必须自行安装 Node 并构建，违背“开箱即用”的目标。

改用 `app-dist` 后：

- 构建产物可以正常提交；
- FastAPI 无需 Node 环境即可直接托管；
- 仓库仍忽略 `frontend/node_modules/` 与 `frontend/.vite/`，不引入依赖垃圾。

## 5. 路由与鉴权

### 5.1 路由表

| 路径 | 名称 | 组件 | 说明 |
| --- | --- | --- | --- |
| `/` | — | — | 重定向到 `/host` |
| `/login` | `login` | `LoginView` | 登录 / 注册 |
| `/host` | `host` | `HostView` | 需主播登录；iframe 加载 `/live-commerce/` |
| `/viewer` | `viewer` | `ViewerView` | iframe 加载 `/viewer` |
| `/:pathMatch(.*)*` | — | — | 兜底重定向到 `/host` |

### 5.2 登录守卫

```js
router.beforeEach(async (to) => {
  if (!to.meta.requiresHost) return true
  const auth = useAuthStore()
  const ok = await auth.ensureSession()
  if (!ok) return { name: 'login', query: { redirect: to.fullPath } }
  return true
})
```

- 守卫只保护 `requiresHost` 路由（当前是 `/host`）；
- `ensureSession()` 请求 `/auth/session`，由后端读取 HttpOnly cookie 判断会话，**不信任 localStorage 里的 token**；
- 未登录跳转 `/login?redirect=/host`，登录成功后回到原目标；
- `sessionChecked` 做单次会话缓存，避免同一会话内重复请求。

### 5.3 登录态存储

| 存储 | 键 | 写入方 | 用途 |
| --- | --- | --- | --- |
| localStorage | `lc_auth_token` | Vue 登录成功后 | iframe 内旧页面建立 WebSocket 时读取 |
| localStorage | `lc_auth_user` | Vue 登录成功后 | 旧页面显示用户名/头像 |
| HttpOnly Cookie | `lc_host_token` | 后端 `/auth/login` | `/live-commerce/` 静态页闸门与 `/auth/session` |

两套存储必须同时存在：Cookie 决定“能不能打开运营台”，localStorage token 决定“iframe 内能不能建立已登录的 WebSocket”。正常从 Vue 登录页进入时，两者由同一次登录同时写入。

### 5.4 与旧登录页的关系

旧登录页 `src/live_commerce/login.html` 与 `/login` 路由保持可用，未被删除。新登录页只是新增入口，便于对比与回滚。两者调用同一套 `/auth/login`、`/auth/register`、`/auth/check`、`/auth/session` 接口，账号体系完全一致。

## 6. 构建与部署

### 6.1 环境要求

- Node.js ≥ 18（本项目验证版本：v24.18.0）
- npm ≥ 9（验证版本：11.16.0）

### 6.2 安装与构建

```bash
cd frontend
npm install
npm run build
```

构建完成后生成 `frontend/app-dist/`。Vite 配置要点：

```js
export default defineConfig({
  base: '/app/',
  plugins: [vue()],
  build: { outDir: 'app-dist', emptyOutDir: true },
})
```

`base: '/app/'` 保证产物中的 JS/CSS 引用带 `/app/` 前缀，与 FastAPI 挂载点一致。

### 6.3 FastAPI 托管

`src/service/service.py` 在模块加载时检查构建目录：

```python
frontend_dist = os.path.normpath(
    os.path.join(os.path.dirname(__file__), "..", "..", "frontend", "app-dist"))
if os.path.isdir(frontend_dist):
    app.mount("/app", StaticFiles(directory=frontend_dist, html=True), name="frontend_app")
```

- 目录存在 → 挂载 `/app`；
- 目录不存在 → 只打印日志，服务照常启动，旧入口不受影响；
- 不修改任何业务路由，不改变 `/live-commerce/`、`/login`、`/viewer`、`/uploads` 的行为。

启动服务后访问：

```
http://127.0.0.1:8085/app/#/login
```

### 6.4 开发态

```bash
cd frontend
npm run dev
```

Vite 默认监听 `5173`，并把以下路径代理到 `127.0.0.1:8085`：

- `/auth`、`/api`、`/uploads`、`/live-commerce`、`/viewer`
- `/ws`（`ws: true`）

开发地址为 `http://127.0.0.1:5173/app/`。iframe 的 `src="/live-commerce/"` 会经代理命中后端，登录 Cookie 与 localStorage 仍在同一 `localhost` 源下。

> 注意：开发态代理目标是 `127.0.0.1`，如果后端跑在 `localhost` 的其他端口，需要同步修改 `vite.config.js`。

## 7. 回滚方案

Phase 1 的所有改动都是**增量**的，回滚不需要改业务代码：

| 回滚目标 | 操作 |
| --- | --- |
| 关闭新入口 | 删除或重命名 `frontend/app-dist/`，重启服务；`/app` 不再挂载，旧入口不受影响 |
| 彻底移除 | 删除 `frontend/`，移除 `service.py` 中的 `/app` 挂载块与 `.gitignore` 两行 |
| 只回滚前端代码 | `git checkout <previous-commit> -- frontend/ src/service/service.py .gitignore` 后重新构建 |

旧入口始终可用：

- `/login` → 原生登录页
- `/live-commerce/` → 原生主播运营台
- `/viewer` → 原生观众 H5

因此迁移期间可以新旧并行，评审时可分别演示。

## 10. 已知限制与后续改进

1. **iframe 内外页面状态不同步**：外壳没有监听 iframe 内部页面切换，浏览器前进/后退只作用于外壳路由。Phase 2 拆分后可消除。
2. **登录退出不完整**：当前 Vue `auth.logout()` 只清 localStorage，未调用后端 `/logout` 清 HttpOnly Cookie；由于登录页暂未提供退出按钮，暂未暴露。后续补退出入口时需同时调用后端。
3. **构建产物入库**：`app-dist` 随源码提交，仓库体积增加约 120KB（JS 111KB + CSS 4KB）；换来评委零构建启动。若后续接入 CI，可改为构建后发布。
4. **未做单元测试**：Phase 1 以构建与手工验证为主；Phase 2 拆分组件后补充 Vitest。
5. **Node 版本差异**：仅在 Node 24 验证，Vite 6 要求 Node ≥ 18；低版本可能触发依赖告警。
