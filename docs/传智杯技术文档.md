## 1. 项目概述

### 1.1 背景

直播带货的业务链条中，主播需要同时处理讲解、上架、答疑、订单和观众反馈，重复性信息处理占据了大量注意力；观众则希望在移动端获得低延迟的公屏互动与即时问答。传统直播间系统通常将运营台与观众端拆成两套服务、两套账号体系，部署与权限维护成本高，且运营数据容易在前后端之间越界泄露。

本项目以"一个服务、两种角色、一条长连接"为设计前提，构建直播电商 AI Agent：主播在桌面端完成直播控制与运营，观众在移动端 H5 完成观看、弹幕互动与下单，AI 负责答疑与运营辅助。

### 1.2 项目定位

| 维度 | 说明 |
| --- | --- |
| 服务对象 | 中小商家与个人主播 |
| 主播端 | 桌面运营台，9 个功能页面（直播控制台、商品管理、弹幕与 AI 问答、商品数据分析、观众列表、私信收件箱、用户评价管理、直播复盘报告、直播系统设置） |
| 观众端 | 移动优先 H5 直播间，商品横条、公屏、下单、私信、评价 |
| AI 能力 | 弹幕问答、话术生成、数据摘要、复盘报告 |
| 通信 | HTTP（登录、静态页面）+ WebSocket 长连接（实时状态、弹幕、订单、私信） |

### 1.3 本版已完成范围

本技术文档第 3～6 章详细描述已经实现并通过自测的三个核心模块：

1. **项目骨架与 WebSocket 基础服务**：分层目录、环境变量模板、服务入口、连接生命周期；
2. **主播 / 观众双角色 JWT 认证与越权修复**：注册登录、HTTP 中间件、WS 握手鉴权、消息白名单与按角色数据裁剪；
3. **直播间弹幕模块**：收发、全房间广播、主播置顶、最近 20 条历史缓存。

商品、订单、钱包、评价、私信与 AI Agent 等业务模块不做逐行级设计说明，但并非黑盒：第 8 章给出系统全貌、Agent 状态图与四条 AI 链路，附录 B 给出全部数据模型、状态机与接口/消息清单，附录 C 给出双端前端的架构与状态同步方式。读者据此可以定位任何一个功能对应的模型、消息与服务端处理入口。

### 1.4 技术栈

| 层次 | 技术 | 说明 |
| --- | --- | --- |
| 运行时 | Python 3.12+ | 使用标准库 `hmac` / `hashlib` 实现 JWT 与口令哈希 |
| Web 框架 | FastAPI + Uvicorn | 同端口托管静态页面、HTTP 接口与 WebSocket |
| 实时通道 | Starlette WebSocket | 每连接独立发送队列，避免并发写 |
| 存储 | SQLite（WAL）+ JSON 文件 | `auth.db`、`viewers.db` 存账号；直播业务数据落 JSON |
| 前端 | 原生 HTML / CSS / JavaScript | 无构建步骤，双端各自单文件 |
| 鉴权 | JWT（HMAC-SHA256）+ PBKDF2-HMAC-SHA256 | 主播 scope 7 天，观众 scope 24 小时 |

## 3. 架构设计

### 3.1 总体架构

系统采用"单服务进程 + 双前端 + 单实时通道"的结构，按职责分为五层：

```
┌──────────────────────────────┐   ┌──────────────────────────────┐
│  主播运营台 /live-commerce/   │   │   观众 H5 直播间 /viewer      │
│  直播控制台 · 商品 · 弹幕 ·   │   │   商品横条 · 公屏 · 下单 ·    │
│  数据 · 私信 · 评价 · 复盘    │   │   私信 · 评价                 │
└───────────────┬──────────────┘   └───────────────┬──────────────┘
                │  HTTP + WebSocket(ws/live-commerce) │
┌───────────────┴──────────────────────────────────┴──────────────┐
│                       服务层 src/service/                        │
│  service.py        HTTP 路由、静态托管、WS 挂载                   │
│  auth_routes.py    主播/观众注册登录                              │
│  auth_middleware.py HTTP 全局 JWT 中间件（按路径要求角色）        │
│  auth.py           主播令牌签发校验（scope=host，7 天）           │
│  viewer_auth.py    观众令牌签发校验（scope=viewer，24 小时）      │
│  live_commerce_ws.py  连接管理、消息分发、广播、按角色推送裁剪    │
└───────────────┬──────────────────────────────────────────────────┘
                │
┌───────────────┴──────────────┐   ┌──────────────────────────────┐
│   数据层 src/data/            │   │   Agent 层 src/agents/        │
│  live_commerce/               │   │  live_commerce_agent/         │
│  商品/弹幕/订单/私信/评价      │   │  问答、话术、摘要、复盘        │
│  SQLite: auth.db, viewers.db  │   │  大模型端点可配置              │
└───────────────────────────────┘   └──────────────────────────────┘
```

分层原则：服务层不承载业务规则，数据层不感知连接，Agent 层不直接操作 WebSocket；三者通过数据管理器交互。

### 3.2 双端同源与实时通道

同一 Uvicorn 进程对外提供：

| 路径 | 类型 | 说明 |
| --- | --- | --- |
| `/health` | HTTP | 健康检查，公开 |
| `/login` | HTTP | 主播登录页，公开 |
| `/live-commerce/` | HTTP | 运营台，要求 host 角色 |
| `/viewer` | HTTP | 观众 H5，公开 |
| `/auth/*` | HTTP | 主播注册登录 |
| `/auth/viewer/*` | HTTP | 观众注册登录 |
| `/ws/live-commerce` | WebSocket | 实时通道 |

WebSocket 连接生命周期：

1. **握手鉴权**：从查询参数（`token` / `host_token` / `access_token`）、`Authorization` 头、Cookie 中提取 token，校验签名、有效期与 scope，得到 `(role, viewer_user_id)`；校验失败直接拒绝握手。
2. **初始状态下发**：`init_state`，按角色裁剪字段。
3. **收发循环**：收包循环识别消息类型 → 角色闸门 → 业务处理 → 回执；所有出站消息进入该连接专属的发送队列，由独立发送循环串行写 socket。
4. **连接回收**：发送循环退出时清理连接、观众索引与在线数。

发送队列的意义：收包循环是 inline `await`，若直接在其中写 socket，慢客户端会阻塞整个循环；独立队列把"处理"与"发送"解耦。

### 3.3 权限模型

权限由四道相互独立的闸门构成，任何一道失守都不会导致越权：

| 闸门 | 位置 | 判定依据 | 失败表现 |
| --- | --- | --- | --- |
| G1 HTTP 中间件 | `auth_middleware.py` | 路径 → 所需角色（host / viewer / any） | 401 + `WWW-Authenticate` |
| G2 WS 握手 | `_resolve_identity` | token 的签名、有效期、`scope` | 握手被拒绝（HTTP 403） |
| G3 消息白名单 | `handle_message` | `_VIEWER_ALLOWED` 集合，未列出即要求 host | `{"code":"forbidden"}` |
| G4 数据裁剪 | `_send_initial_state` / `_broadcast` | 连接角色 | 观众只收到公开字段 |

关键设计：**角色由凭据决定，不由客户端自报**。观众即使发送 `{"role":"host"}` 或伪造 `sender`，也不会获得主播权限或冒充他人身份。

### 3.4 Prompt 控制策略（重点）

AI 协同开发的失败模式集中在四类：**范围漂移**（顺手改无关代码）、**幻觉实现**（声称完成但接口不可用）、**需求静默变更**（用自己的理解替换验收标准）、**不可追溯**（改动混成一次大提交）。本项目的做法是把 Prompt 当作"接口契约"来写，用七条规则约束模型。

#### 3.4.1 规则一：单轮单模块（范围闸门）

每轮 Prompt 首句即划定范围，并在需求前明确"只做本轮功能"：

> 本轮任务：实现主播、观众两套 JWT 身份认证模块，**只做本轮功能，不要额外写其他业务**。

作用：把模型的自由度限制在单一模块内，使本轮改动可审查、可回滚、可对应一次提交。

#### 3.4.2 规则二：需求编号化、验收可观测

需求以编号列表给出，且每一条都落到可观测结果，而不是形容词：

> 1. 接口实现 `/auth/register`、`/auth/login`（host 7 天、viewer）；
> 2. 鉴权中间件：`/live-commerce/` 无 token / 角色不对返回 **401**；
> 3. WebSocket 连接支持 token 鉴权、按白名单裁剪下发数据。

"返回 401"可被测试断言，"做好鉴权"不能。可观测的验收标准使得人工复核不依赖模型自述。

#### 3.4.3 规则三：自测作为交付物

每轮都要求模型自行启动服务、双端连接并验证，而不是只交付代码：

> 自测：启动服务，主播、观众双端连接，测试发弹幕、广播、历史弹幕加载。

这让"完成"的定义从"代码写完"变为"链路跑通"，并暴露出单人分模块开发最易遗漏的跨端问题。

#### 3.4.4 规则四：提交边界即轮次边界

每轮 Prompt 末尾指定 commit message：

> 完成后执行 git 提交，commit message：`feat(danmaku): 实现直播间弹幕收发、广播与弹幕历史缓存`。

作用：一次对话 = 一个模块 = 一次提交，形成第 5 章可追溯的迭代历史；也迫使模型在提交前收敛改动范围。

#### 3.4.5 规则五：审计先行（证据优先）

第二轮的关键设计是要求模型先读现有实现，再决定改什么。模型据此输出的是"已有能力 / 缺口清单"，而不是重写：

- 已有：认证主体、token 签发与校验；
- 缺口 1：角色不符返回 403，与验收标准的 401 冲突；
- 缺口 2：WS 推送事件仍携带运营指标，构成越权泄露。

由此产生了提交 `f3d54ea`——一次典型的"审计后修复"，而不是新功能开发。

#### 3.4.6 规则六：安全默认值写进需求

安全约束在需求阶段显式声明（"按白名单裁剪下发数据"），而不是等实现完成后补补丁。对应到代码即：

```python
# fail-closed：未列入观众白名单的消息类型一律要求 host
if self._roles.get(websocket) != "host" and msg_type not in _VIEWER_ALLOWED:
    await self._send(websocket, "error", {"code": "forbidden", "message": ...})
```

以及身份绑定：

```python
# 身份一律由服务端确定；客户端提交的 userName / role 不参与判定
user_id = await self._require_viewer(websocket, "send_danmaku")
user_name = (acc.userName if acc else "") or "观众"
```

#### 3.4.7 规则七：文档与测试同步

每轮要求把新增接口补入 README 的测试清单（第 2 轮需求第 4 条）。文档因此不是事后补写，而是每轮验收的一部分，保证第 5 章的复现步骤与代码行为一致。

#### 3.4.8 Prompt 模板

综合上述规则，本项目使用的 Prompt 结构为六段式：

| 段落 | 内容 | 控制目的 |
| --- | --- | --- |
| 角色与上下文 | 项目名、形态、技术栈、已有模块 | 减少模型对项目的错误假设 |
| 本轮目标 | 一句话说明本轮模块 | 范围闸门 |
| 约束 | "只做本轮功能，不要额外写其他业务" | 防范围漂移 |
| 需求清单 | 编号 + 可观测验收标准 | 防需求静默变更 |
| 自测要求 | 启动服务、双端连接、给出验证结果 | 防幻觉实现 |
| 交付要求 | 指定 commit message、补文档 | 形成可追溯边界 |

#### 3.4.9 策略效果

| 观察点 | 未约束时的典型风险 | 本项目实际结果 |
| --- | --- | --- |
| 范围 | 一轮改动横跨多个模块 | 每轮改动集中在单一模块，提交可独立审查 |
| 验收 | 以模型自述"已完成"为准 | 每轮均给出可复现的测试输出 |
| 安全 | 权限作为事后补丁 | 白名单、身份绑定、数据裁剪在需求阶段即确定 |
| 追溯 | 一次大提交 | 7 次细粒度提交，消息与需求一一对应 |
| 缺陷 | 隐患被"重写"掩盖 | 第二轮主动暴露并修复两处真实缺陷 |

### 3.5 关键技术决策

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 令牌实现 | 标准库 HMAC 手写 JWT | 不引入第三方加密依赖，审计面小；scope 字段可精确区分双角色 |
| 双角色隔离 | 两套 token + 同一签名密钥 | scope 必须显式校验，避免观众 token 被主播接口接受 |
| 鉴权位置 | HTTP 中间件 + WS 握手 | 静态页面与实时通道是两个入口，必须各自把关 |
| 消息授权 | 白名单 fail-closed | 黑名单会随新增消息类型持续漏；白名单默认更严 |
| 数据下发 | 服务端裁剪 | 前端过滤可被绕过，裁剪必须发生在出口 |
| 存储 | SQLite + JSON | 单机演示零外部依赖，便于复现 |

## 4. 模块详细设计

### 4.1 模块一：项目骨架与 WebSocket 基础服务

#### 4.1.1 目录结构

```
src/
├── run_service.py              # 服务启动入口（加载 .env，启动 uvicorn）
├── service/                    # 服务层
│   ├── service.py              # 路由、静态托管、WS 挂载、启动事件
│   ├── auth.py                 # 主播令牌与口令
│   ├── viewer_auth.py          # 观众令牌与账号
│   ├── auth_middleware.py      # HTTP 全局鉴权中间件
│   ├── auth_routes.py          # /auth/* 接口
│   └── live_commerce_ws.py     # WebSocket 连接管理与消息分发
├── data/live_commerce/         # 数据层（商品、弹幕、订单、私信、评价）
├── agents/live_commerce_agent/ # Agent 层（问答、话术、摘要、复盘）
├── live_commerce/index.html    # 主播运营台（单文件，约 3.6k 行）
└── viewer/index.html           # 观众 H5（单文件，约 1.7k 行）
```

#### 4.1.2 启动链路

1. `run_service.py` 从当前目录加载 `.env`，读取 `HOST` / `PORT` / `MODE`；
2. 启动 uvicorn 加载 `service:app`；
3. 应用启动事件中初始化数据管理器、生成演示数据、注册 WS 端点；
4. 挂载静态目录：`/live-commerce`、`/uploads`；
5. `MODE=dev` 时开启热重载，并在启动参数中为数据目录与 SQLite 文件配置 `reload_excludes`，以降低数据落盘触发重启的概率。

#### 4.1.3 连接管理

`LiveCommerceWSManager` 维护四类状态：

| 状态 | 结构 | 用途 |
| --- | --- | --- |
| `_connections` | 连接集合 | 全房间广播 |
| `_roles` | 连接 → host / viewer | 消息闸门与下发裁剪 |
| `_user_conns` | viewer_user_id → 连接集合 | 定向推送（订单、私信） |
| 发送队列 | 每连接一个 `asyncio.Queue` | 解耦处理与发送，串行写 socket |

消息统一封装为 `{"type": ..., "data": ..., "timestamp": ...}`。

### 4.2 模块二：JWT 双角色认证与越权修复

#### 4.2.1 账号数据模型

| 表 | 字段 | 说明 |
| --- | --- | --- |
| `users`（auth.db） | id, username, email, password_hash, role, is_active, created_at | 主播/运营账号，首个注册者自动为 admin |
| `auth_tokens`（auth.db） | id, user_id, token, expires_at, created_at | 主播令牌记录 |
| `viewer_accounts`（viewers.db） | user_id, nickname, password_hash, avatar, is_active, created_at, last_login_at | 观众账号，`user_id` 形如 `v_xxxxxxxx` |

口令一律使用 PBKDF2-HMAC-SHA256（600,000 轮）加随机盐，格式 `algorithm$iterations$salt$hash`。

#### 4.2.2 令牌设计

| 属性 | 主播 token | 观众 token |
| --- | --- | --- |
| scope | `host` | `viewer` |
| 有效期 | 7 天（604800 秒） | 24 小时（86400 秒） |
| 主体标识 | 整数 `user_id` | 字符串 `sub`（`v_...`） |
| 签发接口 | `/auth/register`、`/auth/login` | `/auth/viewer/register`、`/auth/viewer/login` |
| 校验要求 | scope 必须为 host | scope 必须为 viewer |

两套 token 共用签名密钥，因此**任何鉴权入口都必须校验 scope**：观众 token 的 `sub` 是字符串且无 `user_id`，主播校验路径据此拒绝；反向亦然。

#### 4.2.3 HTTP 鉴权中间件

中间件为纯 ASGI 实现，遍历每个请求，按路径映射所需角色：

| 路径 | 所需角色 |
| --- | --- |
| `/auth/me`、`/admin/*`、`/live-commerce`、`/live-commerce/`、`/live-commerce/index.html` | host |
| `/auth/viewer/me` | viewer |
| `/api/*` | any（需有效 token） |
| 其余公开路径 | 不拦截 |

取 token 顺序：`Authorization: Bearer` → 运营台 Cookie（`lc_host_token`）→ 观众 Cookie（`lc_viewer_token`）。

角色不符与未携带 token 统一返回 **401**（附 `WWW-Authenticate: Bearer`），语义是"需要（重新）登录"，而非"已登录但无权限"，避免客户端继续使用错误身份的 token。

#### 4.2.4 WebSocket 鉴权

握手阶段按以下矩阵判定：

| 客户端输入 | 判定结果 |
| --- | --- |
| 有效主播 token | host |
| 有效观众 token（账号存在且启用） | viewer，绑定 viewer_user_id |
| 无 token，且未自称 host | 游客 viewer（只读公开数据） |
| 无 token，但自称 `role=host` | 拒绝握手 |
| token 签名错误 / 过期 / scope 不符 | 拒绝握手 |
| 自称 viewer 但携带主播 token | 主播（凭据优先于自称） |

#### 4.2.5 越权泄露与修复

第二轮审计发现并修复了两类问题。

**问题一：状态码语义错误。** 角色不符返回 403，与"无 token 或角色不对返回 401"的验收标准冲突，客户端无法据此触发重新登录。

**问题二：WS 数据越权泄露。** 旧实现把完整 `init_state` 下发给所有连接，并原样广播主播侧事件。修复后：

初始状态下发字段对比：

| 连接角色 | 字段 |
| --- | --- |
| host（14 个） | role, liveStatus, currentProduct, products, hostProfile, allDanmaku, pinnedDanmaku, stats, settings, sessions, alerts, highFreqQuestions, reviews, onlineBreakdown |
| viewer（7 个） | role, liveStatus, currentProduct, products, hostProfile, allDanmaku, pinnedDanmaku |

观众的 `liveStatus` 只保留 `status`、`currentStage`、`startTime`、`liveDuration`、`onlineCount`，剥离 `totalAIReplies`、`totalPrivateMessages`、`totalDanmaku` 三个运营指标；商品列表只下发已上架商品。

推送事件裁剪：

| 事件 | 观众侧处理 |
| --- | --- |
| `status_update` | 剥离三项运营统计 |
| `live_started` | 内嵌 `liveStatus` 同样裁剪 |
| `live_ended` | **不下发复盘报告**（GMV、转化、AI 统计） |
| `stage_changed` | 只保留阶段名，剥离运营话术策略 |

#### 4.2.6 接口清单

| 方法 | 路径 | 鉴权 | 说明 |
| --- | --- | --- | --- |
| POST | `/auth/register` | 公开 | 主播账号注册 |
| POST | `/auth/login` | 公开 | 主播登录，返回 7 天 token 并下发 HttpOnly Cookie |
| POST | `/auth/viewer/register` | 公开 | 观众注册，直接签发 24 小时 token |
| POST | `/auth/viewer/login` | 公开 | 观众登录 |
| GET | `/auth/me` | host | 当前主播信息 |
| GET | `/auth/viewer/me` | viewer | 当前观众信息 |
| GET | `/logout` | host | 清除运营台 Cookie |

### 4.3 模块三：弹幕收发、广播与历史缓存

#### 4.3.1 消息协议

发送（客户端 → 服务端）：

```json
{"type":"danmaku","content":"主播好，这个精华液敏感肌能用吗？","sender":"用户名","role":"viewer"}
```

服务端内部归一为 `send_danmaku`，规范化处理：

1. 将除 `type` / `data` 外的顶层字段并入消息数据，兼容扁平结构；
2. 身份由握手凭据确定：主播使用固定 `host_001` 与主播资料；观众必须是已登录账号；
3. 客户端提交的 `sender`、`role`、`userId` 仅作展示字段，不参与身份判定。

广播（服务端 → 所有连接）：

```json
{"type":"new_danmaku","data":{
  "danmakuId":"dm_ws_1793274210700","userId":"v_7f72a327","userName":"观众昵称",
  "content":"主播好，这个精华液敏感肌能用吗？","timestamp":"2026-10-29T19:43:30",
  "isQuestion":true,"isReplied":false,"sender":"观众昵称","role":"viewer"}}
```

广播目标为全房间连接（主播 + 全部观众），发送方自身也会收到，用于统一以服务端数据渲染。

#### 4.3.2 历史缓存

| 项 | 设计 |
| --- | --- |
| 结构 | 内存滚动列表 `live_danmaku_history` |
| 容量 | 20 条（`DANMAKU_HISTORY_LIMIT`） |
| 写入 | 每条弹幕入列表后裁剪到最近 20 条 |
| 清空 | `start_live` 开播时清空，并清除置顶 |
| 拉取 | `{"type":"get_danmaku_history","data":{"limit":20}}` → `danmaku_history` |
| 上限 | `limit` 被钳制在 1–20，客户端无法一次拉取全量 |
| 补充 | 新连接在 `init_state.allDanmaku` 中另获最近 100 条列表数据 |

#### 4.3.3 弹幕置顶

| 消息 | 权限 | 广播 | 说明 |
| --- | --- | --- | --- |
| `pin_danmaku` | 仅 host | `danmaku_pinned` | 置顶指定 `danmakuId`，不存在则返回失败 |
| `unpin_danmaku` | 仅 host | `danmaku_pinned` | 取消置顶 |

广播载荷：`{"pinned":true,"danmakuId":"...","danmaku":{...}}`，取消时为 `pinned:false`、`danmaku:null`。置顶状态随之进入新连接的 `init_state.pinnedDanmaku`，保证中途进入的观众看到同一条置顶。

观众调用 `pin_danmaku` 会被消息闸门拦截：

```json
{"type":"error","data":{"code":"forbidden","message":"无权调用: pin_danmaku"}}
```

前端呈现：主播运营台在「弹幕互动」卡片内为每条弹幕提供置顶 / 取消置顶按钮，卡片顶部显示当前置顶条；观众端在直播间商品横条下方显示固定的 `📌 置顶` 条，并高亮聊天列表中的对应弹幕。两端都只根据 `danmaku_pinned` 广播渲染，不在本地自行改状态。

#### 4.3.4 数据落盘与统计口径

- 真实观众弹幕（`userId` 前缀为 `v_`）计入 `totalDanmaku`，并写入 `danmaku_data.json`；
- 虚拟 / 模拟弹幕不落盘，避免每秒生成的数据反复触发写文件与应用热重载；
- 弹幕是否为提问由服务端判定，问句才触发 AI 自动回复，且回复在后台任务中执行，避免最长 20 秒的模型调用阻塞该连接的收包循环。

| T-13 | 置顶广播 | 主播置顶 | 双端收到 `danmaku_pinned`，新连接可见 | 双端一致，新连接 `init_state` 可见，通过 |
| T-14 | 取消置顶 | 主播取消 | 双端收到 `pinned:false` | 通过 |

### 6.4 测试结论与遗留问题

所有功能模块均在本地环境完成实际运行验证，测试用例可复现；文档内记录各轮迭代对应的实测验证结果。

遗留问题（如实记录）：

1. 前端交互缺少浏览器自动化回归测试，当前依靠静态检查与人工点击验证；

### 7.1 项目亮点

## 8. 系统全貌与 AI Agent 设计

第 4 章按"骨架—认证—弹幕"的顺序展开了三个核心模块。本章补上系统的横向视图：一场直播从开播到复盘经过哪些环节，AI Agent 在哪些位置介入，以及每条 AI 链路的输入、约束与失败兜底。

### 8.1 从开播到复盘：完整业务闭环

| 环节 | 主播动作 | 服务端行为 | 观众侧可见 |
| --- | --- | --- | --- |
| 准备 | 商品入库、上架、选讲解商品 | 写 `products_data.json`；上架变更广播 `product_on_sale` | 商品横条刷新 |
| 开播 | `start_live` | 校验已选讲解商品；划会话边界、重置本场统计；广播 `live_started` | 状态切为直播中 |
| 推进 | `switch_stage` | 更新当前阶段并广播 `stage_changed` | 阶段徽标更新 |
| 讲解 | `set_product` / `generate_script` | 切换当前商品；AI 生成口播稿并记入话术历史 | 讲解商品卡片 |
| 互动 | 弹幕、私信、置顶、转人工、拉黑 | AI 优先回复，规则话术兜底；高频问题计数；定向推送 | 公屏、AI 回复 |
| 成交 | 观众下单、支付、确认收货 | 余额扣款、库存扣减、销量回写；订单状态机流转 | 订单与余额 |
| 评价 | 观众提交评价 | 一单一评；评分汇总回商品 `rating` / `reviewCount` | 评价区 |
| 复盘 | `generate_report`（下播时自动调用） | 按真实口径汇总九个章节，写入 `data/reports/` | 无（主播侧） |

这条闭环的关键设计是**单一数据源**：所有环节都读写在同一个 `LiveCommerceDataManager` 实例的内存模型上，再整体落盘为 JSON；前端不持有业务真相，只渲染服务端推来的快照与增量事件。

### 8.2 直播生命周期与五阶段

直播状态是四值枚举 `idle / live / paused / ended`，迁移规则全部由服务端校验：

| 当前状态 | 消息 | 前置条件 | 结果 |
| --- | --- | --- | --- |
| `idle` / `ended` | `start_live` | 必须已选定讲解商品 | 进入 `live`，记录 `startTime`，重置本场计数 |
| `live` | `pause_live` | 必须处于直播中 | 进入 `paused`，记录 `pausedTime`，停掉定时任务 |
| `paused` | `resume_live` | 必须处于暂停 | 回到 `live`，重启定时任务 |
| `live` / `paused` | `end_live` | 必须处于直播中或暂停 | 进入 `ended`，结算时长，**自动生成复盘报告**并随 `live_ended` 下发 |

五阶段定义在 `LIVE_STAGES`，切换只校验 key 是否合法，允许开播前预置：

| key | 名称 | 阶段策略（同时用于话术提示与弹幕策略） |
| --- | --- | --- |
| `warmup` | 🔥 预热介绍 | 好奇、期待类问题为主，回复侧重商品亮点与福利预告 |
| `flash_sale` | ⚡ 福利秒杀 | 价格、库存、优惠、抢购类问题为主，强调限时与紧迫感 |
| `deep_dive` | 🎯 单品深讲 | 品质、规格、产地、工艺等深度问题，详细讲解细节 |
| `interact` | 💰 互动促单 | 购买意向、下单方式、优惠叠加，引导下单与互动 |
| `closing` | 👋 收尾下播 | 售后、发货、复购、下一场预告，总结本场 |

"开播"与"清空"是两件事：`start_live` **不清空**商品、订单、评价、弹幕集合，只清除本场历史缓冲、置顶、告警与本场真实信号。历史数据跨场留存，"本场 vs 历史"由 `_in_session(startTime)` 判定。这样重启或再开播不会让运营台的订单页和报告凭空少掉一批数据。

### 8.3 Agent 状态图与执行循环

AI Agent 用 LangGraph 的 `StateGraph` 实现，状态类型继承 `MessagesState` 并追加 `remaining_steps`：

```
                    ┌───────────────────────────────┐
                    │ StateModifier：SYSTEM_PROMPT  │
                    │ + 全部历史消息                 │
                    └──────────────┬────────────────┘
                                   ▼
   START ─────────────────────▶ ┌───────┐
                                │ model │◀──────────┐
                                └───┬───┘           │
                     pending_tool_calls             │
                     ┌───────────────┴──────────┐    │
                     ▼                          ▼    │
                ┌─────────┐                    END   │
                │  tools  │──────────────────────────┘
                └─────────┘   工具结果回灌 messages
```

三个实现细节决定了它的可控性：

1. **提示词每轮重注入**：`RunnableLambda` 在每次模型调用前把 `SYSTEM_PROMPT` 拼到消息最前面，多轮工具调用不会因为上下文截断而丢失人设与约束。
2. **工具调用有上限**：`acall_model` 读取 `state["remaining_steps"]`，剩余步数不足 2 且模型仍要调工具时，直接返回"抱歉，处理这个请求需要的步骤较多，请简化一下问题或分步提问 😊"，而不是让循环撞上限后抛异常。
3. **会话日志隔离**：`acall_model` 从 `config["configurable"]["thread_id"]` 取会话键写入 `contextvars.ContextVar`，工具层按会话键读写 `defaultdict(list)`。两个会话并发时，`get_session_log_tool` 不会读到对方的事件。

### 8.4 工具集

`LIVE_COMMERCE_TOOLS` 共 10 个工具，全部为同步函数，由 `ToolNode` 执行：

| 工具 | 入参 | 行为 |
| --- | --- | --- |
| `search_product_tool` | `query` | 按名称、品类、标签模糊检索在库商品 |
| `get_product_detail_tool` | `product_id` | 返回单个商品完整信息（含规格、卖点） |
| `list_all_products_tool` | — | 列出全部商品，供模型做横向对比 |
| `calculate_promotion_tool` | `product_id`, `quantity` | 解析促销文案并计算到手价 |
| `check_stock_tool` | `product_id` | 查询库存与销量，判断是否紧张 |
| `recommend_products_tool` | `category`, `budget`, `scenario` | 按品类、预算、场景三维度推荐 |
| `record_session_log` | `event_type`, `content`, `product_id` | 记录本场事件（讲解、成交、异议等） |
| `get_session_log_tool` | — | 读取本会话已记录事件 |
| `clear_session_log_tool` | — | 清空本会话事件 |
| `generate_report_tool` | `duration_minutes` | 生成本场复盘报告摘要 |

促销计算器支持五种常见文案形态：买 X 送 Y、直降、买 N 减 M、折扣、特惠价。它先做正则匹配再按数量折算单价，匹配不到时原价返回并把促销原文一并给出，避免模型自行"心算"出错。

`SYSTEM_PROMPT` 把"小智"主播的五项能力（商品数据、话术生成、弹幕处理、异议化解、直播记录）写死，并规定查询商品、算价、查库存、推荐、记事件、出报告**必须走工具**，不得凭空报价；同时禁止虚构优惠与承诺。这是把"模型能做什么"收敛到可验证的数据边界内。

### 8.5 模型路由与降级

模型配置不写在代码里，而是存在 `llm_endpoints.json`，由 `llm_endpoint_store` 管理：

| 字段 | 说明 |
| --- | --- |
| `id` / `name` | 端点标识与显示名 |
| `baseUrl` | OpenAI 兼容接口地址，保存时去掉尾部斜杠 |
| `model` | 模型名 |
| `apiKey` | 密钥，**任何出站接口只返回掩码与 `hasApiKey`** |
| `temperature` | 归一化到 `[0, 2]`，非法值回落 0.5 |
| `activeId` | 当前启用的端点 |

`resolve_chat_model()` 的解析顺序是：当前启用端点 → 构造 `ChatOpenAI`（`base_url` + `api_key` + `temperature` + `streaming=True`）；任一必填项缺失或构造失败，记录告警并回退 `.env` 中的 `DEFAULT_MODEL`。设置页的"测试连接"用 15 秒超时、16 个最大 token 发一次最小请求，返回 `{ok, latencyMs, message}`；错误按 401/403/404/429/5xx/网络异常映射成可直接照做的中文提示。

业务侧还有第二层超时：`ai_live._llm_chat` 对每次生成设 20 秒上限，超时、异常、无内容一律返回 `None`，由调用方兜底。**任何 AI 故障都不会阻塞主播流程**，这是整个降级设计的第一原则。

### 8.6 四条 AI 链路

| 链路 | 触发 | 输入 | 输出约束 | 失败兜底 |
| --- | --- | --- | --- | --- |
| 主播话术 | `generate_script` | 商品完整信息 + 6 种话术类型 + 当前阶段 | 100～250 字可直接照念的口播稿 | 内置 `_fallback_script` 模板 |
| 弹幕问答 | 观众发弹幕 | 弹幕原文（截断 200 字）+ 当前商品 | 20～60 字，结合真实商品信息 | 规则话术 + 预设话术匹配 |
| 私信辅助 | `auto_reply_private` | 私信内容 + 当前商品 | 20～60 字，主播口吻 | 规则话术；AI 回复先过敏感词 |
| 摘要 / 复盘 | `generate_danmaku_summary_ai` / `generate_report` | 已算好的统计 JSON | 150～250 字，只准引用给定数字 | 模板拼接；报告本身不调模型 |

**话术生成**的六种类型分别是开场暖场、商品介绍（FAB 法则）、促销逼单、互动提问、异议安抚、收尾下播。`_build_product_context` 把商品压成"名称／品类／价格与原价／库存销量评分／卖点／规格／描述前 300 字"的纯文本，模型不需要理解 JSON 结构。

**弹幕问答**是并发压力最大的一条。观众端弹幕走 `_spawn_danmaku_reply` 后台任务，而不是在收包循环里 `await`——否则一条 20 秒的模型调用会让该连接期间收不到心跳也发不出任何消息。并发由 `Semaphore(3)` 限制，AI 摘要与弹幕回复共用同一个闸门，避免摘要把回复挤掉。AI 回复在落库前还要过一次敏感词检查，违规就退回规则话术。

**私信辅助**与弹幕同构：AI 优先 → 敏感词校验 → 规则话术，区别是回复前会读取该用户会话的等级与历史咨询商品，供前端展示"高意向/潜在/观望"等标签。

**摘要与复盘**是唯一一条"数字先算、模型后写"的链路。`generate_danmaku_summary` 的 system 提示写死"只引用给定 JSON 里的数字与词语，不得编造"，user 传的是统计 JSON 而非弹幕原文合集——让模型自己数弹幕，它一定会编。三级降级为：无真实数据 → 如实返回 `no_real_data`；AI 关闭或失败 → `build_summary_template` 用已算好的数字拼摘要；AI 可用 → 模型组织语言。三者都返回 `success=True`，前端据 `fallback` / `reason` 打"离线摘要"角标，摘要失败不该让按钮报错。

### 8.7 真实数据口径

系统里同时存在真实观众数据与用于营造氛围的模拟数据（虚拟弹幕、模拟订单、虚拟评价）。两者在统计层**按 `userId` 前缀严格分流**：`u001~u010`、`virtual_*`、空 `userId` 归为模拟，其余为真实。

- 实时统计 `LiveStatsData` 的每个字段都由真实事件推导，没有随机漂移；没有埋点数据源的曝光量字段被直接删除，而不是用"在线人数 × 系数"估算。
- 复盘报告九个章节只统计本场真实数据，被排除的模拟量在 `scope.excluded*` 与 `chapter8_conversion.mockOrdersExcluded` 中**显式披露**，让阅读者明白数字为什么是这个量级，而不是当成 bug。
- 没有真实数据时报告显示空态，不会用"时长 3600 秒"之类的兜底值凭空造出一场直播。

这条约束的代价是演示数据的观感不如"漂亮数字"，换来的是报告里每一个数字都能追溯到一条真实记录。

| `soldBase` | int | 历史基数，仅用于展示，不参与真实统计 |
| `isOnSale` / `isInLibrary` | bool | 是否上架、是否在备选商品库 |
| `rating` / `reviewCount` | float / int | 平均评分（0～5）、评价数 |
| `imageUrl` / `images` | str / list | 主图与多图 |
| `tags` / `sellingPoints` / `specs` | list[str] | 标签、卖点、规格（`键: 值`） |
| `description` | str | 详情，喂给模型时截断 300 字 |
| `addedTime` | str | 上架时间，用于稳定排序 |

上架与讲解是两件事：`isOnSale` 控制观众可见性，`currentProductId` 控制"主播正在讲哪件"。开播前只校验后者。

### B.3 订单 `OrderItem` 与状态机

| 字段 | 说明 |
| --- | --- |
| `orderId` / `orderNo` | 内部 ID / 展示编号（`OMS` + 日期 + 序号） |
| `productId` / `productName` / `productImage` | 下单时快照，商品改名不影响历史订单 |
| `userId` / `userName` | 买家；模拟单为空 |
| `quantity` / `unitPrice` / `totalAmount` | 数量、成交单价、总额 |
| `status` | `pending_pay / paid / shipped / completed / refunded / canceled` |
| `payTime` / `shipTime` / `createTime` | 时间戳 |
| `isVirtual` | 是否模拟订单 |

| 起始状态 | 动作 | 目标状态 | 执行方 | 副作用 |
| --- | --- | --- | --- | --- |
| `pending_pay` | 支付 | `paid` | 观众 | 扣余额、扣库存、加销量，记录 `payTime` |
| `pending_pay` | 取消 | `canceled` | 观众 / 主播 | 无（未占用库存） |
| `paid` | 发货 | `shipped` | 主播（仅真实单） | 记录 `shipTime` |
| `shipped` | 确认收货 | `completed` | 观众 | 无 |
| `paid` / `shipped` / `completed` | 退款 | `refunded` | 主播 | 回补库存与销量，金额返充钱包 |

流转规则（服务端强制，前端隐藏按钮不算数）：

1. **下单不扣库存**：`create_viewer_order` 只校验库存与上架状态，生成待付款单并快照商品图；
2. **支付才扣减**：`pay_order` 校验订单归属、状态、是否仍上架、库存、余额，然后扣余额、扣库存、加销量；
3. **发货仅限真实单**：主播 `update_order_status` 只允许 `paid → shipped`，模拟订单不可发货；
4. **退款**：`paid / shipped / completed → refunded`，回补库存与销量，`_credit_viewer` 把金额退回钱包（空 `userId` 安全跳过）；
5. **归属严格相等**：`order.userId != user_id` 一律拒绝，空 `userId` 的模拟单不对任何观众开放。

### B.4 观众钱包 `ViewerAccount`

| 字段 | 说明 |
| --- | --- |
| `userId` / `userName` / `avatar` | 与 `viewers.db` 中的账号一一对应 |
| `balance` | 余额（元），新账户默认 2000.0 |
| `registerTime` | 注册时间 |

充值为模拟充值，金额为正才入账；支付扣款、退款返充都走同一把锁，余额保留两位小数。观众身份只从 JWT 的 `sub` 取，服务端不接受消息里自报的 `userId`，因此不存在"填别人的 id 花别人的钱"的路径。

### B.5 评价 `ReviewItem`

| 字段 | 说明 |
| --- | --- |
| `reviewId` / `userId` / `userName` / `avatar` | 评价人与标识 |
| `content` / `rating` | 正文、1～5 星 |
| `sentiment` | `positive / neutral / negative / question / suggestion`；观众提交时按星级推导 |
| `tags` | 关键词标签 |
| `productId` / `productName` | 关联商品 |
| `source` | `danmaku / private / user`，`user` 表示观众端主动提交 |
| `orderId` | 关联订单，用于归属与防重复 |
| `isHandled` / `images` | 是否已处理、买家秀 |

观众提交评价有三道硬约束：必须带 `orderId`；订单归属必须严格等于当前观众；订单状态必须是 `completed`，且同一订单同一商品只能评价一次。评价成功后重算商品的 `rating` 与 `reviewCount`。

### B.6 私信与会话

`PrivateMessageItem`：`messageId / userId / userName / avatar / content / timestamp / isFromUser / replyType(ai|human|system) / isPreset / presetId`。

`UserSessionItem`：`sessionId / userId / userName / avatar / status / userLevel / lastMessage / lastMessageTime / unreadCount / productId / lastHumanApplyTime / aiFailCount / historyProducts`。

会话状态机与用户等级：

| 维度 | 取值 | 说明 |
| --- | --- | --- |
| 接待状态 | `ai_reception` | AI 自动接待（默认） |
| | `human_reception` | 主播接管，AI 不再自动回复 |
| | `closed` | 会话结束 |
| | `blacklisted` | 已拉黑 |
| 用户等级 | `high_intent` / `potential` / `wait_and_see` / `picky` / `just_ask` | 高意向、潜在、观望、挑剔、随便问问 |

私信自动回复先尝试大模型，回复过敏感词检查后才落库；AI 连续失败达到 `autoTransferThreshold`（默认 2 次）或主播手动操作时转入人工，人工超时 `humanTimeoutMinutes`（默认 8 分钟）后可回落到 AI。预设话术按关键词匹配，命中即用并把 `useCount` 加一。

### B.7 弹幕 `DanmakuItem`

`danmakuId / userId / userName / avatar / content / timestamp / isVirtual / isQuestion / isReplied / replyContent / replyTime / source / isViolation / violationReason`。

`isVirtual` 只在服务端与运营台内部使用，观众端出口数据会剥掉；`isQuestion` 是"是否进入自动回复与高频问题统计"的闸门，避免把闲聊也计入待回复量。

## 附录 C 前端架构与双端状态同步

### C.1 运营台：单文件九页

运营台是 `src/live_commerce/index.html` 一个文件，约 3,600 行，内联 CSS 与 JavaScript，无构建步骤、无依赖包。九个页面通过 `switchPage(page)` 切换，同一时刻只显示一个 `<section>`：

| 页面 | `data-page` | 主要内容 |
| --- | --- | --- |
| 直播控制台 | `console` | 开播/暂停/结束、阶段切换、讲解商品、话术生成、AI 回复 |
| 商品管理 | `products` | 商品增删改、上下架、AI 出图 |
| 弹幕与 AI 问答 | `danmaku` | 实时公屏、置顶、回复、高频问题、AI 摘要 |
| 商品数据分析 | `analysis` | 销量、评分、评价分布（离线 ECharts） |
| 观众列表 | `viewers` | 在线观众、订单数、私信入口 |
| 私信收件箱 | `inbox` | 会话列表、AI/人工切换、预设话术、拉黑 |
| 用户评价管理 | `reviews` | 评价筛选、标记处理、导出 |
| 直播复盘报告 | `report` | 九章复盘、历史报告 |
| 直播系统设置 | `settings` | 直播/弹幕/私信/AI 四组设置、模型端口管理 |

所有业务数据都从 WebSocket 进入，页面本身不发起业务 HTTP 请求；只有登录、头像/图片上传与 AI 出图走 HTTP。

### C.2 观众端：移动优先 H5

`src/viewer/index.html` 约 1,700 行，按手机竖屏布局，三段式结构：

- **舞台区**：主播画面占位、直播状态、阶段徽标、当前讲解商品卡；
- **商品横条**：在售商品横向滑动，点击弹出详情与下单；
- **公屏区**：弹幕墙、置顶弹幕、AI 回复、输入框、私信与"我的"入口。

后端地址由页面顶部的 `LC_API` 配置：同源部署留空即可，跨域部署填 `https://host/backend`，页面用字符串替换推出 `ws(s)://` 地址，因此可整目录拷到 nginx/OSS/CDN 单独托管。

### C.3 状态同步模型

双端共享同一套三段式同步协议：

1. **快照**：连接建立后服务端立即下发 `init_state`，包含角色、直播状态、当前商品、商品列表、主播资料、最近 100 条弹幕、置顶弹幕；主播额外拿到统计、设置、会话、告警、高频问题、真实评价与在线构成。
2. **增量广播**：状态变化以事件推送，如 `live_started`、`stage_changed`、`new_danmaku`、`product_on_sale`、`order_updated`。观众端对商品变更的处理是"重新拉一次商品列表"，而不是在本地合并字段——列表快照比字段级补丁更难写错。
3. **定向回执**：请求类消息只回给发起连接，避免把某个主播的操作结果广播给所有人。

观众端在 `init_state` 中拿到的 `role` 必须消费：若主播 token 过期后连接被降级为观众，前端据此弹阻断层并跳登录页，而不是静默变成只读控制台。

### C.4 双端一致性的四条规则

1. **服务端是唯一真相**：身份、库存、余额、订单状态一律以服务端为准，前端提交的 `userId`、`sender`、`role` 只作展示。
2. **出口裁剪**：同一事件对主播与观众生成不同载荷，`_viewer_safe_event` 只保留公开字段；观众拿不到运营统计、私信会话与设置。
3. **竞态用重拉解决**：运营台"上架 → 立刻讲解"连点时，观众端可能先收到 `product_on_sale`、后收到商品列表，页面会记下 `pendingCurrent` 并在 `get_products_result` 到达后认领，不依赖消息顺序。
4. **断线即重连、过期即降级**：观众端指数退避重连；收到 1008（握手校验失败）时清除本地 token 并以游客身份重连，避免带着坏 token 无限重试；重连后再用 `init_state` 对齐，而不是相信本地缓存。

### C.5 无构建步骤的取舍

双端都是原生 HTML/CSS/JS，代价是没有模块系统与类型检查，约 5,300 行代码集中在一个作用域内；收益是部署只需拷两个文件、评审者打开浏览器就能读源码、离线 ECharts 不依赖 CDN。对竞赛评审与中小商家私有化部署而言，后者更重要。真正需要工程化的部分（鉴权、状态机、统计口径）全部放在服务端 Python 中，前端只做渲染与交互。
